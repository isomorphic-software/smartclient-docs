## KB Topic: Union DataSources

### Description
The UnionDataSource assimilates records from multiple member dataSources, matching fields by name and data type, or by explicit configuration. Different types of member dataSource are allowed, so you can union SQL data with Hibernate data and generic data from a legacy system, for example. For efficiency, SmartClient will use the SQL UNION keyword to achieve the data union for any members dataSources that are [SQL DataSource](sqlDataSource.md#kb-topic-sql-datasources)s; data from any non-SQL members is combined in Java code as a post-process.

Like other dataSource types, unionDataSources can filter, sort and page their bonded data sets, and other dataSource features like [declarative security](../classes/DataSourceField.md#attr-datasourcefieldviewrequires) and [included fields](../classes/DataSourceField.md#attr-datasourcefieldincludefrom) work as you would expect. [Server Summaries](serverSummaries.md#kb-topic-server-summaries) and grouping also work with UnionDS: UnionDataSources that are 100% SQL (ie, their members are all either SQLDataSources or SQLUnionDataSources) get grouping and aggregation built in to the generated SQL statement; UnionDataSources that have some non-SQL members also get grouping/aggregation support, via the automatic manual in-memory grouping and aggregation that is applied to any DataSource implementation that does not advertise built-in grouping support. See [DataSource.suppressManualAggregation](../classes/DataSource_1.md#attr-datasourcesuppressmanualaggregation) for more details of this feature, including how to switch it off if you don't want it

**Example usage**  
UnionDataSource is useful when you need a unified view of data entities that, for whatever reason, you ordinarily keep separate. A plausible example is Customers and Suppliers; those are two distinct entities, and would typically be implmented as separate database tables or Hibernate persistent classes, or whatever. This makes sense: there are lots of things you want to know about a Customer that are not relevant for a Supplier, and vice versa. In most ways, these are not similar things.

However, from a Customs point of view, Customers and Suppliers _are_ similar - they are both Trading Partners. As mentioned above, you probably store lots of things about Customers that you don't store about Suppliers and vice versa, but there will be a set of fields common to both - name, address, country, and financial details like total amount sold or purchased this year. You can use UnionDataSource to provide a "Trading Partners" view of this data.

**Configuration**  
If your member dataSources are very similar, unionDataSource can work in an auto-config mode where all you specify is the list of member dataSource in the unionDataSource's [unionOf](#attr-datasourceunionof) property, and we derive a set of common fields amongst the members where the names and data types match (there is flexibility in this auto-derivation process - see [defaultUnionFieldsStrategy](#attr-datasourcedefaultunionfieldsstrategy)). You can trim this by specifying the list of fields you want to union (again, assuming they have the same name in each member dataSource) using the [unionFields](#attr-datasourceunionfields) property. You can also refine the auto-derived configuration by specifying field definitions in the unionDataSource, using field-level [unionOf](#attr-datasourcefieldunionof) definitions to explicitly declare which member fields should be unioned. You can also use unionDataSource field definitions to optionally rename the unioned field, and do more mundane things, like change the title. Eg,

```
    <field name="tradingPartnerId" unionOf="customerDS.custId,vendorDS.vendorCode" title="Partner ID"/>
 
```
Field attributes on the Union itself have different roles from attributes on its members:

*   **Field identity and composition:** [name](../classes/DataSourceField.md#attr-datasourcefieldname) specifies the public Union field name. [unionOf](#attr-datasourcefieldunionof) identifies the contributing member fields and provides the mapping when their names differ. These references use member DataSource field names, not physical database column names.
*   **Field type:** [type](../classes/DataSourceField.md#attr-datasourcefieldtype) defines the Union field's type and is used in checking compatibility of contributing fields. For a field-level `unionOf` declaration, an omitted type is obtained from a contributing member. Declaring a type is not a request to cast incompatible member data into that type.
*   **Presentation and client behavior:** ordinary field metadata such as [title](../classes/DataSourceField.md#attr-datasourcefieldtitle), [hidden](../classes/DataSourceField.md#attr-datasourcefieldhidden), [detail](../classes/DataSourceField.md#attr-datasourcefielddetail), [valueMap](../classes/DataSourceField.md#attr-datasourcefieldvaluemap), [format](../classes/DataSourceField.md#attr-datasourcefieldformat), and [displayField](../classes/DataSourceField.md#attr-datasourcefielddisplayfield) remains available to components bound to the Union. These settings do not redefine the member fields or their physical storage.
*   **Identity, validation, and access:** ordinary DataSource processing can use [primaryKey](../classes/DataSourceField.md#attr-datasourcefieldprimarykey), [required](../classes/DataSourceField.md#attr-datasourcefieldrequired), [validators](../classes/DataSourceField.md#attr-datasourcefieldvalidators), [canEdit](../classes/DataSourceField.md#attr-datasourcefieldcanedit), and [canView](../classes/DataSourceField.md#attr-datasourcefieldcanview). Field-level viewing restrictions also apply, including [viewRequiresAuthentication](../classes/DataSourceField.md#attr-datasourcefieldviewrequiresauthentication), [viewRequiresRole](../classes/DataSourceField.md#attr-datasourcefieldviewrequiresrole), and [viewRequires](../classes/DataSourceField.md#attr-datasourcefieldviewrequires). These properties retain their ordinary meanings: for example, validators do not filter the rows returned by a fetch, and marking a field as a primary key does not make values from different members unique.
*   **SQL result representation:** [sqlStorageStrategy](#attr-datasourcefieldsqlstoragestrategy) is carried into the generated SQL executor's field schema, along with the field name and type, for SQL-backed Union processing.

This is not a separate whitelist of client field properties: Union fields are ordinary DataSource fields for client metadata purposes. However, retaining a property in the Union field definition does not mean it is forwarded to each member's SQL generation.

In particular, a Union-level [nativeName](#attr-datasourcefieldnativename) does not currently define a common SQL alias for the Union. Member queries use their own native column mappings and alias their output to the public Union field names; the generated SQL executor does not retain the Union field's `nativeName`. Likewise, do not use Union-level [tableName](#attr-datasourcefieldtablename), [customSQL](#attr-datasourcefieldcustomsql), or [customSelectExpression](#attr-datasourcefieldcustomselectexpression) to redefine the SQL source expressions of member fields. Configure physical mappings, SQL expressions, and SQL [includeFrom](../classes/DataSourceField.md#attr-datasourcefieldincludefrom) joins on the member DataSources, then use field-level `unionOf` to expose those member fields under the desired Union names.

**Performance note**  
Ordering and paging with a UnionDataSource only makes sense when applied to the bonded dataset; in order to ensure that we can sort and page the overall dataset correctly, we must fetch every matching record from each member dataSource. For this reason, you should not rely on the paging feature to keep the number of records in the working dataset small; always provide criteria for that purpose. This is a good practice, and one we recommend for any type of dataSource, but it is particularly important with unionDataSource, to avoid situations where we have to fetch thousands or millions of rows from multiple member dataSources, in order to find out which of those rows are in positions 100 to 150 with the current sort settings.
